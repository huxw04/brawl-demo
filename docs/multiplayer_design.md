# 多人联机与乱斗模式设计

状态：阶段 A/B/C、权威复活、比分与结算已完成；进入第一版 3～4 人容量验收与内容收尾
目标版本：局域网 2～4 人自由乱斗原型  
网络拓扑：房主同时担任玩家与权威服务器

本文记录多人模式的长期边界、第一版协议和分阶段验收条件。实现过程中如果改变权威模型、消息语义、tick 规则或复活规则，应先更新本文，避免客户端、服务器和离线战斗各自发展出不同逻辑。

## 1. 第一版目标

第一版多人模式需要做到：

- 一名玩家创建局域网房间，其他玩家输入房主内网 IP 加入；
- 大厅显示玩家名称、英雄、准备状态和连接状态；
- 房主开始比赛，所有玩家进入同一张地图；
- 玩家移动、普攻、Q/W/E/R、长按技能、翻滚和跳跃经服务器确认后执行；
- 服务器权威结算位置、碰撞、伤害、状态、死亡、随机数和胜负；
- 客户端使用权威操作和状态快照维持一致，在差异过大时恢复；
- 支持 2～4 人自由乱斗、死亡倒计时和安全随机复活；
- 房主离开时明确结束对局并返回菜单。

第一版暂不实现：

- 公网大厅、账号、匹配、好友邀请和 NAT 穿透；
- 房主迁移；
- 进行中的比赛加入或断线后恢复原角色；
- 观战、录像下载和服务器列表；
- 完整客户端回滚；
- 专用服务器和反作弊系统。

这些内容不能反向污染第一版协议。例如角色所有权和服务器权威不能因为暂时只有局域网测试而省略。

## 2. 为什么采用混合权威模型

本项目已有 `BattleCommand`、`BattleCommandStream`、`BattleCommandRuntime`、`BattleStateDigest` 和独立 `BattleRng`。网络层应复用它们：客户端上传操作意图，房主排序并广播权威操作，所有机器从同一入口执行。

但不能把 Godot 3D 物理当作跨机器逐位确定的纯锁步模拟。浮点、碰撞顺序、导航和帧调度可能逐渐造成差异。因此采用：

1. **操作序列是主要输入。** 客户端不上传最终位置、命中和伤害；
2. **房主是最终裁判。** 房主运行完整战斗并生成权威状态；
3. **状态快照负责纠偏。** 客户端定期接收位置和战斗状态；
4. **局面摘要负责发现问题。** 摘要不同触发日志或完整恢复；
5. **表现不参与同步。** 粒子、残影、镜头和 `visual_rng` 只在本机播放。

第一版局域网可以让客户端等待服务器确认后再执行操作。确认正确性后，再为本地玩家加入预测和温和校正。

## 3. 网络拓扑与传输

### 3.1 房主模式

- 使用 Godot 高层多人 API 和 `ENetMultiplayerPeer`；
- 房主调用 `create_server`，同时拥有一名本地玩家；
- 加入者调用 `create_client`，连接房主的局域网 IPv4 地址；
- 服务器 peer ID 固定为 `1`；
- 初版端口暂定 UDP `24567`，正式玩家数上限暂定 `4`；该限制是当前玩法和验收范围的应用层配置，并非 ENet 的技术极限；
- 底层额外保留一个只用于完成拒绝握手的连接槽，使第五名玩家能看到“房间已满”。若提高正式人数，仍需重新评估出生点、HUD、比分包大小、房主负载与带宽；
- Windows 首次建立房间可能弹出防火墙提示，试玩说明应提醒只允许专用网络；
- 手动输入 IP 足够完成核心验证，局域网房间自动发现以后再做。

房主和普通客户端运行同一个导出包。网络代码不能假定“服务器没有玩家”，以便将来仍能单独增加无界面的专用服务器入口。

### 3.2 ENet 通道

初版分三个逻辑通道：

| 通道 | 传输方式 | 内容 |
|---|---|---|
| 0 | reliable | 握手、大厅、选人、准备、加载、出生、死亡、复活、计分、比赛结束 |
| 1 | reliable | 客户端操作请求、服务器接受/拒绝结果、权威操作序列 |
| 2 | unreliable | 按角色拆分的高频小型状态快照、服务器 tick、位置与战斗状态纠偏 |

角色快照不能在同一 `unreliable ordered` 通道连续逐个发送：后一个角色包可能使前一个角色包持续被当作旧包丢弃。阶段 C 使用普通 `unreliable`，并由客户端按 `actor_id + server_tick` 独立拒绝倒序旧状态。

完整恢复快照使用 reliable，但与实时操作分开排队，避免大包阻塞操作确认。具体采用额外通道还是分片队列，在实现快照时根据 Godot ENet 测试结果确定。

## 4. 权威边界

客户端只能请求“意图”，例如：

- 移动到世界坐标；
- 普攻某个世界坐标；
- 开始、结束或确认某项技能；
- 沿某个方向翻滚或跳跃；
- 选择英雄、切换准备状态。

客户端不能直接声明：

- 自己或敌人的最终位置；
- 技能已经命中；
- 造成多少伤害；
- 冷却已经结束；
- 获得能量、回血、死亡或复活；
- 随机技能得到了什么结果。

服务器收到操作时至少验证：

- RPC 发送者是否拥有该 `actor_id`；
- 玩家是否已经进入正确的会话和比赛状态；
- 操作序号是否重复、倒退或超过合理窗口；
- 世界坐标和方向是否为有限数值且处于允许范围；
- 角色是否存活、可操控；
- 技能 ID、冷却、资源、形态和释放条件是否合法；
- 单位时间内的操作数量是否超过上限。

peer ID 只代表当前连接，不作为永久战斗实体 ID。服务器维护：

```text
peer_id -> player_id -> actor_id
```

场景节点实例 ID、RID 和对象引用不得进入网络协议或局面存档。

## 5. 网络节点与代码边界

建议新增以下模块：

### `NetworkSession`

固定路径的全局网络入口，负责创建/关闭 peer、连接信号、RPC、协议版本、玩家列表和错误状态。所有 RPC 集中在稳定 NodePath 上，动态英雄节点不直接声明核心 RPC。

### `LobbyState`

保存房间阶段和玩家资料：

```text
player_id
peer_id
display_name
hero_id
ready
connected
is_host
```

大厅资料由房主维护并整体广播。客户端只能请求修改自己的名称、英雄和准备状态。

### `NetworkCommandGateway`

替代场景中“本地控制器直接写入命令流”的连接方式：

- 离线模式：直接提交到本地 `BattleCommandRuntime`；
- 房主模式：本地请求经过同一验证函数，再写入权威流并广播；
- 客户端模式：序列化操作后 RPC 给服务器，等待接受或拒绝；
- Bot：只存在于服务器，生成的命令直接进入服务器验证入口。

### `BattleStateSnapshot`

负责生成和应用可恢复状态。它和 `BattleStateDigest` 分工：Digest 只比较，Snapshot 才能恢复。

### `MatchCoordinator`

服务器权威管理加载、出生、死亡倒计时、复活、比分、比赛时间和结束条件。离线 Bot 战斗也应逐步改为复用这套比赛规则。

## 6. 协议数据

Godot RPC 不直接传输项目中的 `Resource`、`RefCounted` 战斗对象或 `Callable`。所有消息使用只包含基础 Variant、Array、Dictionary 和 PackedArray 的数据包。

`BattleCommand` 增加明确的序列化边界：

```gdscript
func to_packet() -> Dictionary
static func from_packet(packet: Dictionary) -> BattleCommand
```

客户端操作请求至少包含：

```text
protocol_version
match_id
client_sequence
actor_id
command_type
world_target_x/z
direction_x/z
ability_id
pressed_or_released
```

服务器接受后补充：

```text
server_tick
server_sequence
accepted
reject_reason
```

客户端提供的 tick 只能用于测量和诊断，不能决定权威执行时间。服务器把合法操作安排到当前服务器 tick 之后的固定输入延迟窗口，第一版暂定 `2～3` 个 physics tick。

所有浮点输入在进入模拟前检查 `is_finite` 并根据规则量化或限制范围。协议中的枚举使用稳定整数或固定字符串，不传脚本枚举的隐式布局。

## 7. Tick、确认与重发

- 战斗继续使用固定 physics tick，初版为 60 tick/s；
- 服务器维护单调递增的 `server_tick` 和 `server_sequence`；
- 每名客户端维护独立 `client_sequence`；
- 服务器保存最近一段已接受命令，用于重复包去重和诊断；
- 客户端保存尚未确认的命令；超时可以重发相同序号，不能创建新序号伪装新操作；
- 权威命令广播按 `server_sequence` 消费；缺号时短暂等待或请求补发；
- 长按技能必须传输成可靠的 `BEGIN_ABILITY` 与 `END_ABILITY`，断线时服务器主动结束持续输入。

ENet reliable 已负责包重传，但应用层序号仍然必要：它用于去重、日志、重放、拒绝反馈和未来断线恢复。

## 8. 状态快照与校正

### 8.1 小型快照

初版按 `10～15 Hz` 广播：

```text
server_tick
actor_id
position
velocity
facing
hp / stamina / energy
current_ability_id
ability_phase
defeated
```

远端角色在两个快照之间插值显示。第一版本地玩家等待权威操作，也接受服务器位置校正。后续加入预测时可采用暂定规则：很小的误差忽略，中等误差短时间平滑，大误差立即回到权威状态。

### 8.2 完整快照

用于比赛初始状态、检测到不同步和未来重连：

- 地图、规则和英雄定义版本；
- 服务器 tick、命令确认号和 `BattleRng` 状态；
- 所有角色的完整资源、冷却、技能阶段、形态和状态效果；
- 投射物、延迟攻击、棋子、禁锢等持久战斗单位；
- 比分、比赛剩余时间、死亡与复活计时；
- 必要的命中去重和事件序号。

完整快照必须通过明确 ID 重建引用，不能保存 Node、Object、RID 或本机实例 ID。

### 8.3 摘要检查

- 房主周期性广播权威 digest；
- 客户端以同一 tick 的本地状态比较；
- 首次差异记录组件级诊断并请求一次完整快照；
- 连续差异才显示网络异常，避免把单帧接收时序误判为永久失步；
- 摘要不包含纯表现状态。

## 9. 随机数

- 房主在开局生成并广播战斗 seed；
- 战斗逻辑只使用 `BattleRng`；
- 表现随机继续使用每台机器自己的 `visual_rng`；
- 服务器对随机复活、随机技能和掉落拥有最终决定权；
- 随机结果如果会影响战斗，应进入权威事件或完整快照；
- 版本握手必须比较地图、英雄数据和协议版本，避免相同 seed 在不同数据版本下产生不同结果。

## 10. 大地图与自由乱斗规则

第一版建议参数：

- 2～4 名玩家，自由乱斗；
- 首张联机灰盒地图尺寸为 `3000 × 2200 码`，地图内容使用独立 JSON 定义；
- 正式地图预放 `8～12` 个带稳定 ID 的出生点；
- 死亡后 3 秒复活；
- 复活时恢复满生命和满体力；
- 复活后 1.5 秒伤害与控制免疫；角色仍然可见且可被选取，攻击不会产生命中效果；
- 一局 5 分钟，或一名玩家率先达到 10 次击杀；
- 击杀加 1 分，第一版死亡不扣分；
- 同归于尽和环境击杀根据服务器记录的最近伤害来源统一结算。

### 安全随机复活

不直接在整个地图均匀随机坐标。服务器：

1. 从地图定义的合法出生点开始；
2. 排除被墙体、持久危险区或角色 Pushbox 占据的位置；
3. 根据最近敌人距离计算安全权重；
4. 优先保留不在敌人近距离和视野中心的候选点；
5. 使用 `BattleRng` 在候选点中抽取；
6. 广播 `actor_id`、`spawn_point_id` 和 `respawn_tick`。

候选点全部不安全时选择得分最高者并给予完整复活保护，不能无限等待。

## 11. 会话状态机

```text
OFFLINE
  -> HOSTING / CONNECTING
  -> LOBBY
  -> LOADING_MATCH
  -> IN_MATCH
  -> RESULTS
  -> LOBBY 或 OFFLINE
```

- 只有房主可以从 `LOBBY` 进入 `LOADING_MATCH`；
- 第一版要求所有玩家 ready 才能开始；
- 每名客户端加载完成后发送 `PLAYER_LOADED`；
- 房主收齐后广播统一 `START_TICK`，不能让先加载完成的人提前行动；
- 普通客户端断线：服务器移除或击败其角色，并广播 roster 变化；
- 房主断线：客户端停止模拟、显示原因并返回菜单；
- 场景切换和返回菜单必须先正确关闭 `MultiplayerPeer`。

## 12. 版本握手

连接后、进入大厅前比较：

```text
protocol_version
game_version
git_commit（开发包可选）
map_version
hero_schema_version
```

不兼容时拒绝加入并显示明确原因。Godot 高层多人协议只用于相同 Godot 项目之间通讯，不把它当作稳定的第三方服务器协议。

## 13. 分阶段实施与验收

### 阶段 A：最小连接与大厅

实现状态（2026-08-27）：

- `NetworkSession` 已作为固定路径 Autoload 接入，集中维护 ENet peer、协议握手、会话状态、roster 与同步加载确认；
- 主菜单已支持创建房间及输入 IPv4 加入，默认使用 UDP `24567`；
- 大厅已支持玩家名、英雄、准备状态、房主开始、主动退出和错误反馈；
- 房主开始后会广播同一份 match config，双方加载测试地图、按稳定 `actor_id` 各生成一次角色，并在所有客户端回报加载完成后统一进入 `IN_MATCH`；
- 阶段 A 的联机场景不创建玩家控制器，暂时锁定移动和技能输入；
- `scripts/test_network_stage_a.ps1` 会启动两个独立 headless 进程，在 `127.0.0.1:24607` 完成真实 UDP 回归；`scripts/run_local_multiplayer.ps1` 用于启动两个可见窗口手动测试；
- 房主退出后客户端会关闭 peer、显示原因并返回主菜单；普通客户端退出后房主更新 roster 并移除对应展示角色。

实现：

- 主菜单“创建局域网房间”和“加入房间”；
- IP、玩家名、英雄、准备状态；
- 房主开始按钮；
- 连接失败、服务器关闭和主动退出反馈；
- 同步加载一张空战斗地图。

验收：

- 两份 Windows 试玩包在同一局域网连接成功；
- 双方 roster 完全一致；
- 非房主不能开始；
- 房主开始后双方只生成一次各自角色并进入同一场景；
- 任一方退出不会留下无响应界面；
- 这一阶段暂不开放角色操作。

### 阶段 B：双人移动与命令链

实现状态（2026-08-27）：

- 新增 `NetworkCommandGateway`。本地控制器不再直接写网络比赛的命令流，而是提交带 `client_sequence` 的请求；
- 房主验证比赛 ID、操作序号、操作频率、地图坐标、命令类型以及 `peer_id -> actor_id` 所有权，再安排到权威命令流；
- 房主实际执行命令后发送接受/拒绝回执，只有通过执行器的命令才作为权威操作广播；
- 阶段 B 开放右键移动、`S` 停止、`Shift` 翻滚和 `Space` 跳跃，普攻与技能仍由服务器明确拒绝；
- 房主以 12 Hz 在 ENet 通道 2 广播位置、速度和朝向小型快照，客户端对小误差平滑校正、大误差直接恢复；
- 本机双进程测试覆盖房主本地 `call_local` 等价路径、双方移动、连续快速改点、绕墙、停止、跳跃、翻滚、伪造 `actor_id` 拒绝、一次性执行和房主退出恢复；
- 目前客户端等待权威确认，不做本地移动预测。真实局域网测试后再根据手感决定阶段 C 是否提前加入预测。

- 接入 `NetworkCommandGateway`；
- 先同步右键移动、停止、跳跃和翻滚；
- 服务器分配 tick/sequence 并广播接受结果；
- Bot 只在服务器运行。

验收：连续移动、撞墙和快速改点后，两台机器角色位置保持可接受误差，非法 actor_id 操作被拒绝。

### 阶段 C：完整战斗（权威副本重构进行中）

原型状态（2026-08-27）：

- 联机比赛已开放普攻、Q/W/E/R、长按开始/结束、取消技能、停止、移动、翻滚和跳跃，全部复用离线场景的 `BattleCommandRuntime`；
- 房主验证角色所有权、命令类型、技能 ID、序号、频率和坐标，并以连续 `server_sequence` 广播真正执行成功的命令；
- 客户端不使用服务器绝对 tick 排队，而是在下一本地物理 tick 按服务器序号重放，避免两台机器帧进度不同造成长时间延迟；
- 12 Hz 快照已覆盖位置、速度、朝向、生命、体力、能量、冷却、翻滚/受击计时、变身、褚赢棋子充能、状态效果和阵亡；
- 快照按角色拆包以低于 ENet MTU，使用普通 `unreliable`，客户端按角色 tick 去重，并只在对应权威命令已实际处理后应用；
- 联机场景已接入战斗 HUD、技能水位 CD、指向提示与恢复后的圆形体力 UI；
- 本机双进程测试覆盖双方普攻、Cheems 指向 Q、奶龙 Q 取消与 W 长按/松开、CD/状态快照、全部命令类型、角色所有权拒绝和房主退出；
- 五名英雄能复用同一英雄定义和战斗执行器进入联机场景，但客户端重复运行权威命令会在受击、后摇、取消和时钟不同步时产生二次拒绝，不能作为最终结构。

阶段 C 暂停继续补丁式扩展。后续采用“房主唯一权威模拟 + 可靠战斗事件 + 不可靠状态快照 + 客户端只读副本”，具体迁移方案见 [`multiplayer_refactor_plan.md`](multiplayer_refactor_plan.md)。

重构进展（2026-08-27）：

- 房主已成为唯一 `MatchAuthority`，只有房主运行角色物理、命令执行、伤害、CD 和状态结算；
- 客户端已切换为 `MatchReplica`，不再重演权威命令，仅按角色快照恢复位置、朝向、生命、资源、CD、动作、状态和阵亡；
- 双进程 UDP 回归已验证人为篡改客户端坐标、HP 和 CD 后会被下一快照修复，客户端本地命令流不产生战斗历史；
- Cheems Q 已成为首个网络动态实体：可靠事件同步生成/销毁，不可靠完整实体快照同步移动并负责丢事件恢复；客户端只创建无碰撞、无结算的 `ReplicaCombatEntity` 和表现节点；
- 双进程 UDP 回归已验证剑气生成、连续移动、命中、销毁、事件/快照双通道，以及客户端不存在权威 `CombatProjectile`；单进程测试另外覆盖漏生成、漏销毁和跨通道迟到事件；
- 房主现为每个角色维护 `ContinuousAbilitySession`：奶龙 W 和刀盾狗 Q 使用严格匹配且不可重复的 `BEGIN/END`，奶龙 Q 使用 `CAST/CANCEL`；错误命令由权威状态拒绝且不广播；
- 刀盾狗移动取消与松键取消共享 `RELEASE_PENDING`，保留 0.5 秒最短格挡；角色注销、断线或比赛退出会强制清理喷火、格挡和滚动；
- 网络投射物已由 Cheems Q 推广至贝爷飞刀/钩爪、奶龙火球和褚赢锁头棋子；客户端使用统一只读实体及 `ProjectileEventVisual`，钩爪绳索可解析来源角色，所有命中与拉拽仍只由房主结算；
- 可靠生成不会因抢先到达的空快照而被吞掉，后续可靠销毁或下一份完整实体集合会在最多一个快照间隔内清理短寿命投射物；
- 刀盾狗延迟爆炸、褚赢落地/飞行棋子和矩形禁锢现已同步为世界锚定只读实体；客户端不执行二段伤害、飞行路径伤害或禁锢约束；
- 棋盘使用可靠 `world_effect` 事件同步一次性坐标表现，延迟攻击使用带 `detonated` 原因的可靠销毁事件触发冲击波；
- 第二组双进程回归使用刀盾狗与褚赢实战验证世界实体生命周期、棋盘吸附、矩形尺寸和房主权威禁锢；
- 可靠 `hero_effect` 已同步褚赢传送聚气和最终端点、刀盾狗形态切换、Cheems 聚气/法阵/四段次元斩，以及贝爷毒标/延迟爆发/背刺/瞬移轨迹；这些事件只驱动表现，角色位置、形态、状态、伤害和冷却继续以权威快照为准；
- 新增两组双进程回归分别覆盖刀盾狗/贝爷和 Cheems/褚赢，连同原战斗链路与世界实体链路，目前完整检查会运行四组独立 UDP 房主/客户端测试；下一步收口其余角色绑定的一次性普通技能特效，再进入网络故障注入。
- 角色绑定普通表现现已收口：一次性起手使用单个可靠 `ability_vfx`，Cheems W 与奶龙滚动尘土由动作快照驱动本地视觉节奏，奶龙反弹/跳跃/回血、刀盾狗格挡和贝爷钩爪拉拽使用离散可靠事件；
- 形态共用键位的表现事件携带确切 VFX ID，不依赖形态快照与可靠事件的到达顺序。现有双进程测试已加入奶龙 E/R、Cheems W 和刀盾狗实际格挡；阶段 C4 完成，下一步进入 C5 网络故障与恢复测试。
- C5a 已加入确定性接收端故障注入：角色/实体快照可按测试计划丢失、延迟、乱序和重复，可靠事件可重复或投入旧 ID；副本会统计旧包及通过完整集合补回的实体；
- 双进程测试另会真实暂停客户端快照消费后恢复，验证角色状态和漏掉的褚赢禁锢都由后续完整快照收敛；原始 RPC 操作序号测试确认未来包只执行一次，随后到达的旧包和重复包均被房主拒绝；
- C5b 新增第五组 UDP 双进程回归：测试代理持续注入 80–220 ms 抖动、约 30% 快照丢失、乱序快照和重复可靠事件，恢复直连后双方必须收敛到房主权威位置；代理只存在于测试目录，不修改正式通信语义；
- 联机战斗可按 F3 查看权威 tick、命令序列、旧包拒绝和实体快照恢复计数。下一步按 `multiplayer_manual_test_checklist.md` 进行真实双机十分钟对局，再用手感和诊断数据决定是否需要客户端移动预测或更强的恢复包。
- 首轮双窗口试玩暴露的 12 Hz 阶梯移动已在表现层加入速度外推与逐帧插值，奶龙旋转另用本地连续视觉相位；这不是客户端预测，客户端仍不会提前执行自己的操作或进行命中判定。
- 四进程容量测试发现四人完整比分包约 1500 字节，超过 ENet 1392 字节 MTU。角色运动快照继续以 12 Hz、每角色独立 `unreliable` 发送且保持在 MTU 内；比分、计时和网络质量改为每秒一次的 `reliable` 独立消息，击杀与结算仍通过可靠权威事件即时到达。
- 伤害与治疗浮字使用 `combat_feedback` 权威表现事件，携带来源角色、目标角色、类型和实际数值，不让客户端通过血量快照猜测来源。所有客户端接收同一事件，但只显示本机造成的伤害和本机获得的治疗。
- 该拆包调整将协议版本提升至 `2`；当前第一版候选的游戏版本标识为 `0.4.6-v1-candidate`，旧导出包会被版本握手拒绝。

复活规则（2026-08-28）：

- 房主使用独立 `BrawlRespawnManager` 维护死亡和复活，不把比赛规则重新塞入联机场景或角色技能代码；
- 死亡后固定读秒 3 秒，期间输入在客户端入口和房主命令入口都会被拒绝；
- 房主排除被存活角色占据的出生点，按最近敌人距离从最安全的三个候选点加权抽取，并使用比赛 `BattleRng`；
- 复活恢复满生命、满体力并重置角色技能运行态，获得 1.5 秒伤害与控制免疫；角色保持可见，头顶显示“复活保护”；
- `respawn_remaining` 与 `spawn_protection_remaining` 进入角色快照，可靠 `match_rule` 事件同步死亡安排和最终出生点；

### 当前比赛规则与计分同步（0.4.2）

- 房主的 `BrawlScoreManager` 是比赛时钟、击杀/阵亡/助攻、连续击杀、伤害和承伤的唯一写入端；客户端只显示房主同步的结果。
- 当前默认一局 5 分钟或任一玩家先达到 10 次击杀。到时按击杀、助攻、较少阵亡依次判胜；完全相同则平局。
- 助攻窗口为目标阵亡前 10 秒。伤害统计记录实际损失生命，不把溢出伤害计入总量。
- 连杀播报依次为“卧龙出山、一战成名、举世皆惊、天下无敌、诸天灭地”；五连以后重复“诸天灭地”。击杀已有三连杀的玩家时，“终结”覆盖普通播报。
- `kill_announcement` 与 `match_ended` 使用可靠权威事件；倒计时和完整统计随普通状态快照同步。比赛结束后双方立即关闭输入和命令接收，但仍保留房间连接，方便查看结算。
- HUD 默认只显示自己的 K/D/A，按住 `Tab` 展开全榜、松开收起。榜首 Wi-Fi 图标表示该玩家到房主的 RTT：房主为 0 ms，其他玩家由房主测量并同步；它不表示两个客户端之间不存在的直连延迟。结算面板额外显示全员伤害和承伤。
- 击杀播报使用双方英雄头像与玩家 ID，中间显示“一破·卧龙出山、双连·一战成名”等完整连破文案和击杀图标；触发终结时用“终结”覆盖连破文案。
- 联机 HUD 不再假设只有一名敌人，因此删除屏幕顶部的自己/敌人血条、状态条和双份体力条。生命、英雄资源和状态沿用角色头顶表现，体力改为角色画面左侧的世界空间浅蓝圆环；阵营颜色只作用于血条和脚底关系圈，不再给敌方立绘整体套红色滤镜。
- “局域网战斗”状态、在线名单、命令确认和诊断计数统一收进左下角 `F3` 面板；全局击杀播报缩小后位于屏幕上方中央。

下一阶段改善公网手感时，优先给本地移动加入客户端预测与服务器校正，并保留技能命中、伤害和随机结果的房主权威。远端角色继续使用插值；按键起手可以先播放不影响判定的即时反馈。
- 本地角色复活时相机直接切到新出生点，HUD 显示死亡倒计时；
- 单进程测试覆盖安全选点、完整恢复、保护期和权威事件，独立 UDP 双进程测试覆盖倒计时、远端复活、保护状态和事件各消费一次。

下一步实现击杀归属、比分、比赛计时和结算。

- 大地图、出生点、安全随机复活、比分、计时和结算；
- 扩展到 3～4 台电脑；

## 14. 测试策略

- 继续运行所有离线战斗测试，网络层不能改变技能语义；
- 为序列化做往返测试：`command == from_packet(to_packet(command))`；
- 测试伪造 actor_id、重复序号、非法坐标、过量操作和错误技能；
- 在一个 SceneTree 的不同子树挂独立 `MultiplayerAPI`，做快速自动化服务器/客户端测试；
- 再用两个独立导出进程做真实 UDP 冒烟测试；
- 保存服务器命令日志、seed、版本和摘要差异，保证问题可复现；
- 网络测试需要覆盖房主也是玩家的 `call_local` 路径，避免房主操作执行两次或完全不执行。

## 15. 当前已确定与待决定事项
