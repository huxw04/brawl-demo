# 乱斗框架设计基线

这份文档是后续开发的长期约定。改变核心规则时，应先更新本文，避免角色各自实现一套互不兼容的战斗逻辑。

## 1. 当前目标

构建一个容易调试、容易添加英雄的 2.5D 斜俯视乱斗框架。空间、碰撞和地图使用 Godot 3D；角色图片、序列帧动画和 UI 可以继续使用 2D 表现。

首个灰盒版本包含地面八方向移动、跳跃、带无敌帧的翻滚、生命/体力/能量/CD、近战与投射物、三维 Hitbox/Hurtbox、墙体，以及角色实验室和玩家对 Bot 的战斗场景。

## 2. 不可破坏的架构边界

### 英雄定义（数据）

英雄定义只描述数值、技能列表和表现资源，不读取键盘、不寻找对手、不直接操作场景 UI。

### CombatActor（通用实体）

玩家、Bot 和测试角色共用同一个 `CharacterBody3D` 实体。实体持有位置、朝向、生命、体力、能量、当前动作和冷却。控制者只能提交移动和动作意图。

能量/充能属于可选英雄资源：只有 `max_energy > 0` 且配置了状态资源标识的英雄才显示 HUD 与头顶资源条；不使用该机制的英雄不保留装饰性的空条。

### AbilityDefinition / AbilityRunner（技能规则）

普攻也是技能。技能统一经历 `startup -> active -> recovery`，定义消耗、冷却、三维判定体积、伤害、击退、能量收益以及是否生成投射物。动画和特效响应阶段事件，不能自行结算伤害。

### 场景（编排）

角色实验室可以绕过释放条件，但仍调用真正的技能执行器。战斗场景负责生成角色、接入玩家或 Bot 控制器、显示 HUD 和判断胜负，不复制技能逻辑。

## 3. 2.5D 空间与摄像机

战斗世界使用 Godot 3D 坐标：地面为 `X/Z`，高度为 `Y`。固定 `Camera3D` 以正交斜俯视方式观察场地。禁止使用屏幕像素坐标参与战斗判断；屏幕坐标只用于 CanvasLayer UI。

调试尺度约定为 `1 世界单位 = 1 地图格 = 100 码`。这是便于沟通的游戏单位，不对应现实米制；Lab 在场地左下角显示一段 100 码标尺。英雄与技能文档优先同时记录世界单位/格数，避免用屏幕像素或“看起来几格”描述范围。

角色使用面向摄像机的 `Sprite3D`，因此正式素材仍可采用 2D 图片、Sprite Sheet 和八方向动画。Sprite3D 是表现节点，不能决定碰撞和伤害。

角色移动、跳跃、墙体、投射物和判定体积都存在于同一个 3D 空间。攻击定义地面横向宽度、身前纵深、最低和最高高度。角色跳跃时 Hurtbox 随 CharacterBody3D 上升，命中由 Area3D 的空间重叠决定。

第一版跳跃期间保留水平控制，翻滚保持在地面并在配置窗口内无敌。能否越过矮墙由真实跳跃轨迹、墙高和碰撞层决定，不能用屏幕位置猜测。

## 4. 战斗判定

- **Hurtbox / Area3D**：目标可受击体积；
- **Hitbox / Area3D**：技能造成命中的体积；
- **Pushbox / CharacterBody3D**：角色、地面和墙体的实体碰撞；
- **Sensor / Area3D 或 RayCast3D**：AI 感知、拾取、预警和视线；
- **World / StaticBody3D**：地板、墙体和不可移动障碍物。

每次技能释放生成唯一 `attack_id`。一个 Hitbox 默认对每个目标只结算一次。命中流程为：3D 体积重叠 → 阵营/所有者过滤 → 无敌过滤 → 命中去重 → 伤害/击退/能量 → 战斗事件与表现。

## 5. 资源规则

- 生命用于胜负；
- 体力目前只由翻滚消耗；移动和跳跃期间均可正常恢复；
- 能量由造成伤害和受到伤害获得；
- 技能冷却在释放成功时开始；
- 条件不满足时动作不能启动，UI 应给出反馈。

当前规则：翻滚固定消耗最大体力的 `1/3`，并触发恢复延迟；跳跃不消耗体力，移动、跳跃和待机期间均可正常恢复。疾跑及其输入、命令类型已经删除，常态移动直接使用原疾跑速度。具体数值仍属于手感参数。

## 6. 动画与时间轴

技能时间轴是规则权威。阶段变化可触发动画、音效、粒子、拖影、镜头震动和命中特效。更换动画或播放速度时，不应改变伤害判定。

正式美术使用 `Sprite3D` 承载 2D 图片或 Sprite Sheet，并用 `AnimationPlayer` / `AnimationTree` 控制 idle、move、jump、fall、roll、attack、cast、hurt、defeat。灰盒阶段使用占位纹理与颜色/缩放展示相同事件。

## 7. 地图与墙体

- 地板和墙体使用 `StaticBody3D`；
- 墙高是规则数据，会影响角色、投射物、射线和技能体积；
- 子弹默认撞击 World 层后销毁；
- 可破坏墙体以后使用独立战斗实体，拥有 Hurtbox、生命、阵营和破坏事件；
- Bot 的距离计算和寻路使用 X/Z 平面，复杂地图接入 `NavigationRegion3D`；
- 遮挡、穿墙、跳墙由碰撞层或技能属性明确配置。

## 8. Bot 基线

当前 Bot 使用可解释的效用规则，根据距离、冷却、能量和危险程度选择接近、拉开、翻滚、普攻或技能。它和玩家只在意图来源上不同。

## 9. 代码质量与扩展约定

- 新英雄优先新增定义和资源，不在通用实体中按英雄名写分支；
- 新机制若能被多个英雄复用，先抽象为技能效果或状态效果；
- 投射物、陷阱、召唤物记录 owner、team、source ability 和生命周期；
- 调试场景和正式战斗必须复用同一条执行路径；
- 战斗代码不得依赖 Camera3D 位置、屏幕投影或 UI 坐标；
- 2D 素材通过 Sprite3D/AnimationPlayer 接入，不为素材形状改写通用空间规则；
- 每次加入英雄，至少在实验室检查所有动作，并在战斗场景完成一次对局。

## 10. 近期里程碑

1. 将占位英雄和两个测试场景迁移到统一 3D 空间；
2. 用高墙、矮墙验证角色、投射物和技能碰撞；
3. 调整移动、跳跃、翻滚和攻击节奏；
4. 接入第一个正式角色 Cheems 的分层静态精灵与技能原型（机制第一版已完成，正式分层图待参考素材）；
5. 将静态表现拆成动作帧，并继续校准状态效果、取消窗口和地图交互；
6. 再决定多人乱斗、地图机关、手柄和网络同步范围。

## 11. 操控与命令流

默认操控采用 MOBA 形式：右键点击地面提交移动目标，左键进行普通攻击或确认一个已经进入瞄准状态的指向技能；`Q/W/E/R` 选择四个技能槽，`R` 为大招；`Shift` 翻滚，`Space` 跳跃。改键页面以后实现，当前输入映射集中在控制器中，不能写入英雄脚本。

UI 和本地输入不能直接修改 CombatActor。所有离散操作先转换为 `BattleCommand`，至少记录：战斗 tick、单调递增序号、操作者、操作类型、世界目标点、方向、技能 ID 和布尔状态。离线、Bot、回放和未来网络输入共用同一消费入口。

Lab、Bot 战斗和未来权威服务器统一由 `BattleCommandRuntime` 推进 tick、按 actor ID 路由命令并驱动 `CommandMotor`。Lab 右侧动作按钮也必须提交 `BattleCommand`；“忽略消耗与 CD”只是一项本地调试规则，不能绕过命令入口。运行器会为每条命令产生接受/拒绝结果，后续网络层可直接把它扩展成服务器确认，而不再复制一套技能调用逻辑。

持续寻路本身不是每帧一条网络命令：右键只提交目标世界坐标，控制器按照确定的地图网格计算路径并持续产生移动意图。技能选择属于本地 UI 状态，最终确认施法时才形成战斗命令。

需要“沿当前移动方向立即释放”的技能不在执行帧临时读取键盘。输入控制器会把当时的移动方向写入 `BattleCommand.direction`，命令执行器先按该方向转身再停止寻路并释放技能；静止时使用当前角色朝向。这样快速位移的手感与未来回放、网络重演保持一致。

右键移动反馈属于非确定性的表现层：点击位置立即产生短促波纹，寻路器返回的实际可达终点显示持续地面圆环；到达、阵亡、重置或其它动作替换移动后圆环消失。不可达目标只显示橙红色叉号。表现节点监听共享命令运行时产生的请求位置、解析终点和可达结果，不参与战斗摘要与操作序列。

指向技能进入瞄准状态后，由 `AbilityTargetingPreview` 在真实 X/Z 地面绘制半透明提示。通用类型包括直线弹道、前方矩形、位移路径、圆形选点、单位锁定和自定义禁锢矩形；范围优先复用技能的真实判定框、弹道寿命、位移距离与施法距离。边界使用具有世界宽度的透明带而非单像素线，正常填充透明度约 4%、边界约 22%，最大范围与次级范围更淡；方向范围在末端收尖并带有内部箭纹，圆形落点带中心环和短刻度。越界或无合法目标才改为橙红色。提示只读取本地鼠标和战斗状态，不生成命令，也不进入确定性摘要。

普通攻击命令允许在命令执行器中缓存一个目标点：若目标点在普攻圆形索敌范围外，先寻路接近；进入范围后若缓存仍未被移动、技能或翻滚命令覆盖，则转向附近敌人并执行普攻。缓存属于可序列化输入的派生状态，不改变 Hitbox 的真实半径。

## 12. 联机与确定性边界

目标网络结构采用服务器权威：客户端上传带序号的操作，服务器按 tick 接受、排序和执行，并周期性下发权威状态；客户端可做预测，发现校验差异后回滚或校正。重发操作序列用于丢包恢复，但不能把 Godot 3D 物理视为跨平台逐位确定。

为支持回放和排查：

- 战斗使用固定 physics tick；
- 命令具有 tick、sequence 和 actor ID；
- 每局保存初始 seed、地图版本、英雄定义版本和命令序列；
- 战斗逻辑禁止调用全局 `randf/randi/randomize`；
- 随机技能只能从战斗局部 RNG 或明确的随机流获取结果；
- 权威端应记录随机结果或保证相同流以相同顺序消费；
- 当前 `BattleStateDigest` 会对位置、速度、朝向、资源、技能阶段、CD、状态和 RNG 状态进行量化并生成校验值；网络实现阶段再加入快照、确认号与重发窗口。

## 13. 状态效果边界

状态效果采用通用定义和运行时实例，不在 CombatActor 中为每个英雄技能写分支。定义至少包含 ID、持续时间、标签、堆叠规则、属性修正、周期和表现标签；实例保存来源、剩余时间、层数和下一次周期 tick。

框架只预留通用查询和事件，例如 `move_speed` 倍率、`stunned`、`control_immune`、`untargetable`、周期伤害。具体状态清单、叠层和驱散规则随正式英雄逐步补充。

头顶信息遵循“必须立即读懂的状态优先”：眩晕、霸体、无法选中或定身临时替换角色名；血条始终保留。减速、中毒等可从运动或持续掉血感知的状态使用脚底色环、角色染色和受伤闪烁，buff 栏以后再补。多个强提示状态并存时，优先级为无法选中、眩晕/定身、霸体。

## 14. 英雄目录与实验室切换

英雄通过 `HeroCatalog` 注册。Lab 的下拉框只负责选择定义，切换时重新创建 `CombatActor`、命令执行器和玩家控制器，避免旧角色的碰撞节点、状态和信号残留。Lab 与实战必须继续共享 MOBA 输入和 `BattleCommandStream`，动作按钮只作为绕过条件的调试入口。

英雄美术放在 `assets/heroes/<hero_id>/`：`references/` 保存带来源说明的参考图，不参与运行；`sprites/`、`vfx/`、`audio/` 保存正式运行资源。不得直接把来源不明的网络二创作为游戏资源。
