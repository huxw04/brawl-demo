# 多人战斗重构规划

状态：R3 离线权威基础完成，阶段 C5b 持续网络劣化自动测试完成，等待真人局域网验收  
日期：2026-08-27

本文记录阶段 C 暴露出的结构问题、目标架构和迁移顺序。重构期间以保住现有五名英雄、Lab、Bot 战斗和阶段 A/B 房间链路为前提，不用一次性重写整个项目。

## 1. 当前结论

阶段 A 的创建房间、IP 加入、大厅、选人、准备、同步加载和断开处理可以保留。阶段 B 的输入命令、角色所有权检查、服务器序号和移动快照也具有继续使用的价值。

阶段 C 当前采用“房主运行战斗，再把同一命令交给客户端重新运行”的方式。这个边界无法可靠支持完整战斗：

- 客户端会按自己的受击、后摇、CD 和技能阶段再次判断服务器已经接受的命令，可能二次拒绝；
- Godot 物理、导航、帧调度和浮点碰撞不能保证跨进程逐位确定；
- 服务器 tick 和客户端本地 tick 不是同一个时钟；
- 投射物、棋子、禁锢、延迟攻击和法阵等持久实体只有本地 Node，没有网络稳定 ID；
- 快照只纠正角色的一部分结果，无法完整解释“为什么出现这个动画、命中和实体”；
- 表现与规则混在 `CombatActor`，客户端无法只播放权威结果而不重新结算规则。

因此阶段 C 不再继续叠加特判，改为明确的房主权威状态复制模型。

## 3. 目标权威模型

```text
本地输入 / Bot 决策
        │
        ▼
InputCommand（玩家意图）
        │
        ▼
MatchAuthority（仅房主或离线本机运行）
        ├── 校验并推进 CombatWorld
        ├── 生成、更新、销毁网络战斗实体
        ├── 产生 AuthoritativeEvent
        └── 周期生成 StateSnapshot
                    │
          ┌─────────┴─────────┐
          ▼                   ▼
房主本地 Presentation    客户端 ReplicaWorld
                              │
                              ▼
                       Presentation / HUD
```

核心规则：

- 伤害、命中、CD、资源、状态、死亡和实体生命周期只由 `MatchAuthority` 决定；
- 客户端不再调用完整技能规则验证权威结果；
- 权威事件决定一次性表现，快照负责持续状态和纠偏；
- 服务器 tick 只用于排序、时间标记和插值，客户端不把它当作自己的绝对执行 tick；
- 所有会持续存在或影响玩法的对象都有稳定 `entity_id`；
- 纯特效随机数留在本机，战斗随机数只在权威世界中使用；
- Lab 和 Bot 战斗运行“本地 MatchAuthority”，确保离线与联机不形成两套技能规则。

## 4. 三类网络消息

### 4.1 InputCommand

客户端发给房主的意图：

```text
client_sequence
match_id
actor_id
command_type
ability_id
target / direction
pressed / released
```

它不能包含伤害、命中、最终坐标或 CD 结果。

### 4.2 AuthoritativeEvent

可靠、有序的一次性事实：

```text
event_id
server_tick
event_type
source_actor_id
target_actor_id
ability_id
entity_id
position / direction
payload
```

首批事件类型：

- `ABILITY_STARTED`、`ABILITY_CANCELLED`、`ABILITY_FINISHED`；
- `HIT_LANDED`、`HEALED`、`STATUS_ADDED`、`STATUS_REMOVED`；
- `ENTITY_SPAWNED`、`ENTITY_TRIGGERED`、`ENTITY_DESPAWNED`；
- `ACTOR_DEFEATED`、以后加入 `ACTOR_RESPAWNED`。

事件驱动拔刀、挥刀、受击闪烁、爆炸、声音等不能仅靠连续快照可靠表达的表现。

### 4.3 StateSnapshot

不可靠、高频、可覆盖的持续状态：

- `server_tick` 与最近事件号；
- 角色位置、速度、朝向、生命、资源、CD；
- 当前动作 ID、阶段和剩余时间；
- 状态效果和形态；
- 活跃网络实体的位置与必要状态；
- 阵亡状态和权威复活计时；比分仍待加入。

快照按角色或实体分片，客户端按对象 ID 和 tick 独立去重。快照不得依赖“前一个不可靠包一定收到”。

## 6. `CombatActor` 的迁移方法

不能一次把所有调用者改掉。保留 `CombatActor` 作为兼容门面，外部暂时仍可调用 `try_ability()`、`receive_hit()` 和读取 `hp`。内部实现逐步委托给组件。

推荐拆分顺序：

1. **先拆纯表现。** 把约一半的 `_spawn_*`、Sprite 分层、动作姿势和死亡表现迁到 `ActorPresentation` 与五个 HeroVfx；不改变战斗结果。
2. **再拆英雄专用机制。** 把 Bear、奶龙、褚赢、变身和 Cheems 特殊逻辑迁到 `HeroRuntime`，通过固定 hooks 接入。
3. **再拆通用动作与状态。** 把技能时间轴、资源/CD 和伤害结算从 CharacterBody 中分离。
4. **最后改网络边界。** 此时客户端可以只持有 ReplicaState 和 Presentation，不需要伪装成完整权威 `CombatActor`。

HeroRuntime 第一版接口可以保持很小：

```text
on_ability_start(context)
on_ability_activate(context)
on_ability_tick(context, delta)
on_ability_cancel(context)
on_hit(context)
on_kill(context)
write_snapshot()/restore_snapshot()
```

不要把每个技能都变成一个零散 Node；先按英雄拆专用机制，只有可复用或有独立生命周期的对象才继续拆分。

- 单进程副本测试覆盖全部事件的去重、角色 ID 解析和关键表现节点；新增两组双进程 UDP 回归，分别实战验证刀盾狗/贝爷与 Cheems/褚赢，确认变身、毒标、延迟爆发、背刺、四段次元斩和传送端点在双方各消费一次。

#### C4d：角色绑定普通技能表现收口（2026-08-27）

- 通用技能激活路径只为确实拥有一次性附属特效的技能发送一个可靠 `ability_vfx`；纯角色分层动作、投射物、世界实体和已经单独事件化的技能不会重复发送，避免把每次普攻姿态或每帧动画塞进可靠通道；
- `ability_vfx` 同时携带逻辑键位和确切 `ability_vfx_id`。刀盾狗常态/变身技能即使事件早于形态快照到达，表现层也能从完整英雄定义中选中正确版本，不依赖当前副本恰好已经切换形态；
- Cheems W 只可靠同步一次开始和持续时间，房主与客户端的 `CheemsVfx` 各自以 0.09 秒视觉节奏生成多层横向剑气；表现观察到权威动作结束后会提前停止，不产生二十余条可靠网络消息；
- 奶龙 Q 的滚动尘土直接由只读动作阶段和同步滚动方向在本地生成；普攻冲击波、喷火口和大笑走通用一次性事件，撞墙反弹、E 起跳/最终落点和 R 每次回血走带权威世界坐标的离散事件；
- 刀盾狗格挡成功使用独立确认事件，E 盾影和变身 E 冲击波走通用事件；贝爷近战、隐身、毒刀旋风走通用事件，钩爪命中后的实际拉拽起终点另行可靠同步；
- 副本测试覆盖普通/变身同键技能的乱序消歧、Cheems W 本地节奏、奶龙离散事件、格挡和钩爪拉拽。现有双进程对局扩展为真实验证 Cheems W、奶龙滚动/喷火/跳跃/回血和刀盾狗正面格挡，无需新增只测假事件的网络场景。

C4 的动态实体、世界实体、长动作和角色绑定普通表现至此形成完整权威边界。下一步进入 C5，加入延迟、丢包、乱序、重复可靠事件和快照中断恢复测试，再进行真人局域网长时间对局。

### C5：网络故障测试

- 注入延迟、丢包、乱序和重复输入；
- 验证可靠事件去重、不可靠快照覆盖和完整恢复；
- 最后再做真人局域网十分钟连续对局。

#### C5a：确定性故障注入与真实接收中断（2026-08-27）

- 新增 `network_fault_injection_test.gd`，在 `MatchReplica` 接收边界按指定到达时间投递角色快照、完整实体快照和可靠事件，稳定复现长时间丢包、延迟、乱序和重复，而不依赖操作系统网络环境；
- 角色快照测试连续丢弃前九个 tick，再以 `10 → 12 → 11 → 重复 12` 到达，确认只接受前进 tick，旧包和重复包不会回滚位置或生命；
- 实体测试覆盖漏可靠生成后由完整快照补回、乱序运动快照不回退、漏可靠销毁后由下一完整空集合清理，以及“空快照先到、短寿命可靠生成后到”时先显示再由下一快照限制陈旧寿命；
- 可靠事件测试确认重复生成/销毁不会复制实体或表现；ENet 可靠通道 1 保证同通道有序，测试仍人工投入旧事件，接收端会按全局事件 ID 安全拒绝而不重播过时特效；
- `MatchReplica` 新增旧角色快照、旧实体快照、旧可靠事件、快照补生成和快照补销毁计数，为后续局域网诊断提供可观察数据；
- 真实双进程基础对局会暂时断开客户端角色快照消费，篡改位置/生命/CD，确认中断期间不被本地模拟改变，恢复监听后由下一份权威快照收敛；
- 世界实体对局会同时丢弃褚赢 R 的可靠生成事件和若干完整实体快照，确认重新接收后无需重放技能即可从下一完整集合恢复禁锢副本；
- 客户端还会通过真实 RPC 依次发送“未来操作序号、较旧序号、未来序号重复包”，验证房主只执行未来 STOP 一次，并分别拒绝倒退和重复请求。

C5a 验证了协议自身的恢复边界。下一批 C5b 使用真实局域网或系统网络模拟工具加入持续延迟、抖动和比例丢包，记录上述诊断计数与位置误差，并运行至少十分钟真人对局；这部分不应通过在正式代码里随机丢包来模拟。

#### C5b：持续劣化双进程测试与现场诊断（2026-08-28）

- 新增仅供测试使用的 `NetworkImpairmentProxy`，在客户端已经解码的消息与 `NetworkMatch` 消费者之间持续注入 80–220 ms 延迟、抖动、约 30% 角色/实体快照丢失和确定性乱序；正式 `NetworkSession` 与 ENet 参数不包含随机丢包代码；
- 可靠事件保持有序且不丢失，只增加固定延迟和少量重复副本，符合可靠通道语义并验证事件 ID 幂等；
- 新的双进程用例让双方在劣化期间连续换点移动、滚动并释放 Cheems Q，确认仍有快照持续前进、旧快照被拒绝、客户端不生成权威投射物；恢复直连后，双方必须回到房主权威指定的最终位置；
- 联机战斗按 F3 可显示只读诊断面板。房主显示权威 tick、命令序列和实体数；客户端显示旧角色/实体/事件计数、快照补建/补删计数和当前只读实体数；
- 首轮导出试玩确认客户端直接显示 12 Hz 快照会产生规律性顿挫；角色副本现使用权威速度做最多 120 ms 短时外推并逐帧追赶快照目标，动态实体根据相邻权威位置估算表现速度。生命、命中、CD、墙体和技能阶段仍只取房主结果，传送或大误差会直接校正；
- 大厅默认名改为“所选英雄_四位随机数”，自动名随英雄切换，手动编辑后保持不变；连接不存在的房间最多等待六秒并返回带原因的主菜单；非持续指向技能松键不再误发 `END_ABILITY`；
- 主菜单可在玩家名右侧直接选择创建/加入房间所用英雄，自动名使用灰白色、手动名使用白色；房主地址只展示按常见家庭/校园网段排序的一个建议 IPv4，并提示必要时以 `ipconfig` 为准，避免把虚拟网卡地址全部堆入界面；
- 奶龙滚动与摆尾的旋转改为表现层逐帧累计相位，不再依赖 12 Hz 的权威 `action_elapsed`；褚赢禁锢现在参与奶龙 E 的权威终点求解，框外目标会使用最后合法框内点，因此角色、伤害和落地特效不会分离；
- 完整回归现在包含第五组独立 UDP 双进程测试，专门覆盖持续劣化与恢复；
- 真人局域网验收步骤和记录模板见 `docs/multiplayer_manual_test_checklist.md`。
